## 复利审计纪律（2026-09-13，SOP S6）

**教训9：算术年化 ≠ 复利到手。因子报告强制并列"算术年化 + 复利累计"，复利累计为正才有资格谈 alpha。**

- 实测：mom120 SPY 口径算术年化净 +7.72%，但 2016-2026 复利累计净 **-10.73%**（IR 0.367，日波动 ~2.65%，方差拖拽 ~8.85pp/年，把算术 alpha 全吃光还倒贴）。
- mom250 算术 +10.78% → 复利 +21.92%（≈+2.0%/年，弱正）。
- **只报算术年化、不报复利累计，与"只报等权净超额"同罪**——都是把波动率的幻觉当 alpha（几何均值 = 算术均值 − σ²/2）。
- SOP S6：任何因子过五关（IC/IR/换手/单调/净收益）之前，先过复利审计：`prod(1+日净)−1` 为正，才进入下一关；kill-rule 的"累计超额"一律用复利累计口径。

## 口径三问（2026-09-13，硬规范）

**教训10：同一天两次口径事故（上午 SPY 列混口径、下午熔断权益混子账户）→ 任何数值使用前必注明三要素，缺一不算数。**

1. **资产范围**：全账户 totalEq / 子账户（引擎/合约）/ 人工仓剔除后的「自动部分净值」——三者不可混。
2. **基准**：等权宇宙 / SPY（市值加权）——同一策略两种基准是两个数。
3. **频率**：算术年化（μ×252）/ 复利累计（prod(1+r)−1）——真实账户走复利。
4. **分母**：任何「胜率/连亏」先问分母是**交易日 / 日历日 / 逐笔交易**——"胜率 7%"是日频（含空仓日）、"逐笔胜率"是 ~30%，两者差一个量级。

**2026-09-13 董事长错误修正记录（入档）**：曾据"胜率 7%"推出"最长连亏 20-50 笔、熔断冲突、按 28 笔签"——被逐笔实测推翻：7% 是日频胜率，逐笔胜率 ~30%，最长连亏实为 2-8 笔（"28"是 SOL 交易总数）。教训即上面第 4 条。

## 教训11（2026-09-14 立）：任何"好得不正常"的数字，先查 lookahead，再谈结论

- 4H 多时间框架首跑 BTC Sharpe 2.06，"好得不正常"——自查发现日线方向当日映射到当日 4H（前视偏差），加一天滞后重跑后真实值 1.43。
- **铁规**：任何数字若"好得不正常"，第一件事不是兴奋，是查 lookahead（信号用到了当日/未来数据）；查完无前视，再谈结论。
- 多时间框架尤其易犯：高频入场信号（4H）若用了低频方向信号（日线）的"当日"值，就是前视——低频信号必须滞后一个低频周期（日线方向滞后 1 天）。

## 教训12（2026-09-14 立）：组合净收益 = E[pos×ret]，禁止拆成 E[pos]×E[ret]

- **第三起口径事故**（前两起：SPY 列混基准 / 熔断权益混子账户）：台账组合口径用 product-of-sums `clip(Σw·pos)×(Σw·ret)`，即 E[pos]×E[ret]，把 Cov(pos,ret) 交叉项丢了。
- 波动率目标让 pos 与 ret **负相关**（低波标的拿高仓、涨幅却小）→ Cov<0 → E[pos]×E[ret] 比真实 E[pos×ret] **虚高**。
- 实测：日线四标全样本，B 口径（product-of-sums）月均 +2.96% vs A 口径（逐标的 net）**+2.18%**，虚高 0.78pp；其中 **0.685pp 是 Cov 交叉项**，成本口径只差 0.007pp。
- **硬规**：组合净收益一律用 **E[pos×ret]**（逐标的 pos×ret 加权求和）口径，禁止拆成 E[pos]×E[ret]。任何组合数字进台账前先过这道检查。

## 教训13（2026-09-20 立）：retry 状态消息最多重试 3 次，无限重试循环禁止

- **事故**：钉钉桥（ding-bridge）因 DSH 主引擎 09-14 重启后 `agents.list()` 返回 0（无主会话可代理），把 inbox 里 `status=retry` 的消息每 10s 无限重试，outbox 刷了数百条"稍后自动重试"，钉钉消息洪流。
- **止血**：inbox 里 retry 消息改 failed + 清 outbox 洪流；**防复发**：桥插件 `index.js` 加 retryCount，retry 最多 3 次，3 次后转 failed 且只推一次失败通知。
- **硬规**：任何消息队列的 retry 状态最多重试 3 次，3 次后转 failed 且只推一次失败通知——无限重试循环从此禁止。

## 教训14（2026-09-23 立）："机器睡过头"的根因是我们自己的脚本睡回去

- **现象**：07:35-07:55 早班任务连续多天 11:41 后才跑，怀疑联想 PCManager 覆盖电源设置。
- **真相**：`USTailClose`（03:52）跑 `_wake_close.py`，尾盘清仓后调用 `SetSuspendState` **主动把电脑睡回**（事件日志：Sleep Reason = Application API），一觉睡到 11:41 被 USB 设备弄醒。睡眠根因是自伤，不是联想。
- **修复**：删掉 `_wake_close.py` 的"睡回"；机器 24 小时跑量化，不睡。
- **教训**：排查"系统行为异常"先查自己的守护/定时脚本有没有副作用动作（睡回、关机、杀进程），再怀疑外部因素。"永不休眠"策略一直是对的，是自家脚本亲手把电脑按睡了。
